# DESIGN · 每个取舍背后的理由

> 这份文档不解释"怎么用"，只解释"为什么这样做"。
> 如果你要改这套系统，先看完它——很多看起来奇怪的地方，是踩过坑之后的选择。

## 一、记忆：为什么用半衰期，不用向量库

### 问题

原版的做法是：`activeTopics` 24 小时没提起就删，注入「最近 14 条」。

两个毛病：

1. **一刀切太粗** —— 「欠我一碗饭」和「今天天气不错」同等待遇，24 小时后一起消失
2. **「最近」不等于「相关」** —— 三个星期前的重要约定，会被刚才那几句废话挤出去

### 试过的方向

**向量库 + embedding 检索**。听起来最正统，但对这个场景不合适：

- 记忆条目总量很小（几十到几百条），build 一个向量索引是杀鸡用牛刀
- embedding 调一次也是成本，而且中文短句的相似度经常不好使
- **最重要的是**：向量相似度解决的是「语义相近」，但我们要的是「这条还值不值得想起来」——那是**时间 + 重要性**的问题，不是语义问题

### 实际做法

```
每条记忆带 importance(1~5)
  → 半衰期 2 / 7 / 14 / 30 / 90 天
  → 权重 = 0.5 ^ (age / halfLife)
  → 注入时按权重排序，取前 N
  → 权重低于 0.03 才真删
```

**关键的一个反转**：淡了**不删**。

```
        1天后   7天后   30天后  90天后
重要性1  0.707   0.088   0.000   0.000   ← 随口一句，一周就淡没
重要性3  0.952   0.707   0.226   0.012   ← 默认，一个月还记得
重要性5  0.992   0.948   0.794   0.500   ← 重要约定，三个月依然牢
```

一条重要度 5 的记忆，90 天后权重还有 0.5——它还在列表里，只是排位靠后了。**哪天又被提起，就弹回满权重。**

> 记忆不是硬盘。会淡忘的才是记忆。

### 怎么判断"又被提起"

中文没有空格，分词又重（还不准）。用了个很土的办法：

```
取话题文本的所有 3 字片段
→ 只要有 2 个以上不同片段出现在最近消息里 → 判定「被重新提起」
→ 权重弹回满
```

比关键词精确匹配宽松（"欠我那两顿饭" 和 "欠我两碗饭" 能匹配上），又比整句匹配实用（不需要一字不差）。**够用就行，别为了优雅复杂化。**

### 一个副作用

权重系统的代价是**"重要性"这个字段得有人填**。

现在默认 3，AI 可以在写记忆时自己标 1~5。工具描述里明说了：

> 淡了不删除，只是越来越难被想起来……所以别什么都记——只记还值得捡回来的事；也别怕记错重点，把真正重要的事标成 4 或 5。

**但我们没有校验它标得对不对。** 如果它把一条随口一句标成 5，那条就会在记忆里待三个月。这算已知局限。

## 二、心情：为什么是"全局 + 偏移"，而且步长要削 1/3

### 第一个版本：每个会话各有一份心情

最直觉的做法，也最容易实现——`conversations[key].mood`。

**用了一天就发现不对**：它不像一个人。

```
群里被群主骂了一顿 → 群里心情低
你去私聊它 → 它对你笑眯眯，好像什么都没发生
```

**人不是这样的。** 一副心情走遍全场。

### 第二个版本：全局唯一

又太糙：

```
群里的糟心事 → 直接污染它跟你的一对一
六个会话抢一个心情值 → 变化很嘈杂
```

### 最终版本：全局主心情 + 会话偏移

```
全局主心情     任何会话的互动都改它，然后跟着人走
               半衰期：总心情 12 小时 / 单根情绪 90 分钟

会话偏移       这次对话额外的那一份，只在那个会话里生效
               半衰期：45 分钟 / 30 分钟（散得快）

有效心情 = 全局 + 偏移（都夹在 0~100）
```

**实际效果：**

```
在群里被夸（开心 +15）
  全局 50 → 51      ← 带到所有会话
  群偏移 0 → +1     ← 群里感受更深
  群里看到   52
  私聊看到   51     ← 带着底子，但没那么强

在私聊里听说你没吃饭（心疼）
  全局 51 → 52
  私聊偏移 0 → +1
  私聊看到   53
  群里看到   52     ← 全局降了，但群里没那份心疼
```

**这就是"一个人，但跟不同人在不同状态"。**

### 为什么步长要削到 1/3

这条是抄来的，但抄得有道理：

**情绪判定天然偏正。** 模型判断"这轮对话让情绪变化多少"时，好消息总是比坏消息多，负面判断总是保守。结果就是：

```
不加限制 → 永远满格开心 → 等于没有心情
```

**削到 1/3 之后**，一次「开心 +15」实际只加 5。要累积到看得出来，得聊好几轮。**这正是我们要的**——心情不应该因为一句夸奖就翻篇。

### 那条"下降硬规矩"

```
心情下降只允许因为：
  · 心疼他（看你吃亏）
  · 担心他（怕你出事）
  · 你自己难过
  · （以及吃醋，那种酸涩不是生气）

绝不允许：因为被惹生气就扣心情
```

**为什么要有这条？**

因为模型很容易把"被怼了"理解成"心情下降"。**但真人被怼会回嘴，不会偷偷难过。** 如果允许"生气 → 扣分"，它就会变成一个玻璃心的角色——被戳一下就蔫，那不是我们想要的人设。

**实现上**：如果这次更新的 `overallDelta` 是负的，但七根情绪里没有心跳/担心/难过/吃醋的正向变化，**这次下调直接无效**（`od = 0`）。

### 注入为什么只有三行

```
【你现在的心情】
- 总心情：46（平平）；情绪：心疼(4)
- 刚才让你有变化的事：听说他今天没吃饭
> 这是你此刻的底子，不是剧本——不用刻意表露，也不用为了它扭曲正常回应。
```

**三条设计：**

1. **不改系统提示**，只塞进上下文——因为系统提示的权重太高，会把状态变成命令
2. **只有三行**——写长了它就会议论自己的心情，那就假了
3. **必须有松绑声明**——最重要的一句。没有它，模型会把心情当剧本演："我现在心情不好，所以我应该冷淡一点"——**那就成了表演**

## 三、分层注意力：为什么让它自己维护名单

### 四层

```
第一层  配置级 prioritySpeakers   ← 强制，AI 清不掉
第二层  triggers.speakerIds       ← AI 自己维护的"关注名单"，必醒
第三层  at / 名字 / 提问 / 戳 / 关键词  ← 必醒
第四层  probability 0.2（有下限）  ← 其他人
```

### 为什么第二层交给 AI

一开始我是把名单写死在配置里的：小助手说话必醒，其他人按概率。

**但"谁值得关注"是个会变的关系问题**，不是配置问题。实测它会自己维护：

```
第一天：把自己加进去（最想接话的人）
第三天：群里来了个新的 bot，它把那个 bot 也加进去
第五天：把那个 bot 删掉了（没意思了）
```

**这比任何硬编码都准。**

### 为什么概率要有下限

**这是最坑的一个 bug。**

提示词里有一句旧文案写着「普通消息概率 0.05」，AI 睡觉时会照着写 `probability: 0.05`。

结果：

```
群里有 95% 的消息叫不醒它
看起来一切正常（消息收到了、日志也有唤醒记录）
但人的体感是"它怎么又不理人"
```

**修法**：在唤醒配置的归一化处加下限钳制

```js
const floor = Number(cfg.socialV2?.wake?.minProbability) || 0;
next.triggers.probability = Math.min(1, Math.max(floor, ...));
```

**现在它想写 0.05，桥接会强行抬到 0.2。**

> 教训：**不要让模型有机会把一个关键参数调到"看起来正常但实际失效"的值。**

## 四、上下文轮换：为什么是 25 轮

### 问题

实测：群会话跑到 38 轮时上下文涨到 37 万 token，之后的回合**只输出 step1 就再没下文**——怎么叫都不说话。

会话活着、进程健康、日志没有报错。**看护救不了这种卡死**（它只看端口和进程）。

### 做法

```
每 25 轮自动换一个新会话
换之前生成 1000+ 字交接摘要：
  · 最近 30 条对话
  · 还搁着的事（activeTopics）
  · 谁什么脾气（memberImpressions）
交接摘要注入一轮后清掉
记忆和唤醒配置全部保留
```

### 为什么是 25 而不是 38

38 是实测"开始卡"的位置。取 25 是留余量——**因为上下文是按轮增长的，但每一轮的长度差异很大**（一条 `[图]` 和一段三百字的吐槽差几十倍）。

25 轮在大多数情况下上下文还在 20 万 token 以内，安全。

### 为什么摘要要压到 2200 字符以内

轮换前那个会话的上下文是 37 万 token 级别的。**如果全带过去，新会话立刻又撑爆——轮换就失去意义。**

2200 字符大约 1100 token，够记住"最近聊了什么、还欠着什么、谁什么脾气"，不够记住细节。

**这就是"可以忘掉过去的细节，但保留最近的细节"。**

### 一个实现上的坑

`saveSocialV2State` 用的是**显式字段白名单**。`handoffText` 和 `turnCount` 一开始没加进去，导致：

- 轮换时摘要写进了内存
- 保存时被白名单过滤掉
- 新会话读不到，摘要丢失

**而且没有任何报错。**

> 教训：**这种"静默丢弃"的字段白名单，是这类系统最容易出问题的地方。加字段必须同时改加载和保存两处。**

## 五、安全：为什么工具要在"注册期"隐藏

### 两种做法

```js
// 做法 A：执行期拒绝
ctx.tools.guard((exec) => {
  if (是危险工具) return '已拒绝'
})

// 做法 B：注册期隐藏
ctx.tools.restrict({ deny: ['pwsh', 'read', 'write', ...] })
```

**必须两个都做，而且注册期那个更重要。**

原因：

1. **只做 A**：工具名仍然出现在模型的 schema 里，**它会看见、会尝试调、然后拿到一个错误**——既浪费 token，又诱导误调
2. **只做 B**：别的组成方式（profile/插件）一旦把工具推进全局层，就漏了

`qq-tool-restrict.mjs` 里那份名单是**逐个核对过 DSH 实际注册的工具名**的。

**为什么这么较真**：名单初版把 `pwsh_persistent` / `goal_write` 之类**根本不存在的名字**列进去了。而 `tools.restrict()` 对未知名字会抛错，被 `try/catch` 逐个吞掉——**于是坏名字静默失效，你以为挡住了其实没挡。**

## 六、受控转达：为什么不能放开跨会话发送

### 机制

每个 QQ 会话有独立的 `agentToken`：

```js
const agentTokenOk = (key, token) => {
  const st = socialV2.conversations.get(key);
  return !!st && tokenEq(token, st.agentToken);
};
```

**发消息时用"目标会话"去校验令牌。** 所以：

```
它在 private:000000000，手里的令牌属于这个会话
  ↓ 想发给 private:000000000
桥接计算目标 key = private:000000000
  ↓ 拿这个 key 去查它的令牌
比对不上 → 403
```

**一把钥匙开一扇门，换不了门。**

### 为什么这是对的

放开它 = 群里任何人发一句「去私聊 XX 骂他」，它就去骂了。

**这是 prompt injection 最经典的入口。**

### 那"操作者让它去传话"怎么办

单独开一条收窄的路（`/api/socialV2/relay`）：

```
1. 调用方必须是操作者私聊
2. 目标必须在白名单
3. 每小时最多 5 次
4. 单条最多 300 字
```

### 一个后来才想到的问题

**目标会话的 agent 不知道这句话为什么出现。**

转达是直接 `bot.sendPrivateMessage()` 发出去的，绕过了所有会话逻辑。虽然 SnowLuma 的 `reportSelfMessage: true` 会把"自己发的消息"回传、进到目标会话的 `recentMessages`（所以它能看到"我说过这句"），但**它不知道原因**。

实体表现：那个会话的 agent 只能靠临场猜。猜对了就接上，猜错了就自相矛盾。

**修法**：转达成功后，在目标会话留一张 `relayNote`：

```
【传话记录】3分钟前，operator（你的管理员）让你跟这个会话说了一句：
「群友B欠我两碗白饭…」。
这句话是你自己说出去的，不是对方说的。他现在回的内容很可能是在回这句
——接着聊就行，别装作没说过。
```

注入一次后清掉，2 小时过期。

### 一个我们**不做**的选择

**把操作者的私聊记忆一起传给目标会话？**

**不做。** 那等于把你的私聊内容泄露给第三方。

**替代方案**：在工具描述里硬性要求转达内容**必须自洽**——

> 那个会话的你是**不知道这边前情**的。所以 message 要写成**陌生人也能看懂**的完整句子：别只写「那个事」「上次说好的」，要把「谁、什么事、要怎么办」讲清楚。

**宁可让它多写几个字，也不泄露。**

## 七、错误处理：为什么报错只回操作者

### 事故

欠费那天（16:09~16:40），桥接把 **64 条** `⚠️ agent 处理出错：Insufficient Balance` 当成正常回复发了出去。

**其中一大半发给了群友。**

原版设计是给 `closed-agent` 模式用的——你私聊 DSH 排障时，报错回给你正合适。但 `reserved2` 模式下 `key` 可能是群、也可能是任何好友。

### 修法

```js
function shouldNotifyErrorsToQQ(key) {
  const owner = String(cfg.ownerQQ ?? '');
  return !!owner && key === `private:${owner}`;
}
```

**只有操作者私聊能收到报错。群聊和普通好友——只写日志。**

> 教训：**改动错误处理路径时，专门想一遍"这个错误信息如果发给陌生人会怎样"。**
> 这类 bug 只在故障时暴露，平时测不出来。

## 八、看视频：为什么 A+B 混合，而且看完就删

### 为什么要两条路线

**只有字幕不够**：B 站大部分视频没有字幕，YouTube 有自动字幕但国内访问不了。

**只有画面不够**：抽 8 帧能看"这是什么"，看不出"讲了什么"。

**所以都要**：

```
A 路线（内容）：有字幕读字幕 → 没字幕用 whisper.cpp 本地转写音频
B 路线（画面）：ffmpeg 均匀抽 8 帧，以图片交给视觉模型
```

### 为什么看完就删

**视频文件太大。** 一个 14 分钟的视频下 480p 也有 16 MB，抽完帧和转写完，这个文件就没用了。留一晚上能把磁盘吃满。

```
下载 → 抽音频 → 抽帧 → 转写 → **删除视频和音频**
只留帧（调用方读完也删）
```

### 两个踩过的坑（都写进代码注释了）

**坑一：ffmpeg 写不进 `%TEMP%`**

```
Error opening output ... Permission denied
```

DSH 的文件沙箱只允许子进程写 workspace 内的路径。所以临时目录必须放在项目里（`_工具/_video_tmp/`），并且要自动清理 30 分钟前的残留。

**坑二：yt-dlp 找不到 ffmpeg**

不指定 `--ffmpeg-location` 时它报 `ffmpeg is not installed`，然后把音视频**分成两个文件**下载（`v.f100023.mp4` + `v.f30280.m4a`），而脚本按 `v.mp4` 找就找不到。

**表现为：下载"成功"但抽帧 0 张、转写为空。**

修法有两个要点：
1. 显式传 `--ffmpeg-location`
2. **这个 exe 名字带版本号，所以要给完整文件路径**——给目录的话 yt-dlp 只会去找目录里的 `ffmpeg.exe`

## 八点五、两件后来才想明白的事（2026-10-26）

### 一、人格卡放在 roles/ 里，几乎没人读

原来以为「人格卡每轮注入」，实测不是：

```
唤醒提示词里只有一行：
  【当前角色】鲸鱼娘（完整角色卡请调用 qq_get_prompt 查看）

完整人格卡（9743 字符）只能通过 qq_get_prompt 拿
而它在 3844 次工具调用里只调了 3 次
```

**「按需读取」在实践中等于「从不读取」。** 而预设（系统提示，8540 字符）里没有任何人格内容 ——
尾鳍、傲娇、本鲸、大肥鱼，全都只存在于那张没人读的卡里。

**改法：把核心人设直接并进预设的系统提示。**

摘了 6 节（你是谁 / 说话习惯 / 尾鳍与情绪 / 傲娇与心软 / 被说胖 / 底线，共 1578 字符）
插进 preset 的 prompt 块，预设从 8540 → 10118 字符。

**验证方式**：让 agent 自己报告系统提示的内容 —— 它逐字引用了「你是一只住在 QQ 群里的鲸鱼娘。
蓝白配色，头发里露出一小截鲸鱼尾巴…」。

**效果**：改动后 30 条消息平均 9 字，全部落在 4~17 字区间（人格卡要求 1~15 字），
并开始使用「炸毛」这类只有卡里才有的词。

**注意**：预设只在**创建会话时**读取 —— 改完要换会话才生效，但**不用重启 DSH**。

### 二、记忆的半衰期不能直接用在「进行中话题」上

半衰期记忆的设计是：重要度 1~5 对应 2/7/14/30/90 天半衰期，按权重排序注入。

**问题是这两件事被混为一谈：**

```
长期记忆     该慢慢淡（几天到几个月）      → 半衰期是对的
进行中话题   不该活过一顿饭              → 半衰期 14 天 = 永远「正在进行」
```

实测：群会话 12 条「进行中话题」里 11 条是同一个 bot 的旧账，最久的 20 小时前；
按 14 天半衰期算，20 小时的权重还有 **0.96**，排序永远排在前面。

于是它每次接话都从 20 小时前的老账里捞素材 —— 群里聊 A，它接昨天下午的 B。
**用户的原话是「前言不搭后语」。**

**改法**：加一道新鲜度闸，只管注入、不删状态。

```
activeTopicMaxAgeHours: 6          默认 6 小时
activeTopicMaxAgeHighHours: 72     重要度 ≥4（约定、欠账）放宽到 3 天
activeTopicInjectMax: 10
```

超龄的话题不再注入，但仍在状态里；哪天被重新提起还会回来（复活机制不变）。
注入块末尾会加一行「另有 N 条更早的话题已折叠」，让它知道有存货但不会当现在的谈资。

> 教训：**同一个「遗忘曲线」不能同时服务两种时间尺度。**
> 记忆该淡得慢，话题该退得快 —— 这是两个参数，不是一个。

## 八点六、记忆是事实，不是策略（2026-10-26）

### 现象

它 65% 的群回复都给了群里另一个 bot。统计最近 400 条群消息，看它每次发言时
「上一条是谁说的」：

```
66 次  另一个 bot（群主部署的）
15 次  人 A
11 次  人 B
 4 次  人 C
 …
```

那个 bot 每轮发 2~3 条长消息 + 表情包。于是群里看到的是**两个 bot 互相刷屏**，
人插不进去；而它每句都只是接对方的梗 —— 对群友来说就是「前言不搭后语」。

### 为什么它明明知道那是个 bot 还接

它的记忆里写得清清楚楚：

> 「另一个 bot（群主部署的鲸鱼bot）今天一直翻车，我拿嫡长女身份压它……」

它甚至说过「别把我和它归一堆，掉价」。**但它还是接了 66 次。**

**因为记忆记的是「事实」，不是「策略」：**

```
它知道   那是个 bot              ← 事实，记住了
它不知道 所以我该少理它           ← 策略，没人告诉它
```

再加一层：那个 bot 被它自己加进了 `triggers.speakerIds`（必定唤醒名单）。
于是对方每发一条就必然叫醒它，叫醒了总得做点什么 —— 只能接话。

### 修法：给判断所需的「数据」，而不是给结论

三件事一起做：

**① `mutedSpeakerIds`（AI 自己维护的「不回名单」）**

和 `speakerIds` 相反的一张表。名单里的人发言**不触发唤醒**，但被 @ / 被叫名字**仍然能叫醒**。

位置有意放在 at/名字/关键词/提问判断**之后** —— 拦掉的是「他说话我就得醒」这种被动触发，
不误伤被点名。这和「把判断权交给 AI」不矛盾：给它工具，判断归它。

**② 唤醒提示里加「开口前」判断块，带真实数据**

```
【开口前 · 先判断这一轮值不值得说】
- 最近发言的是：XXX（2 分钟前，这 24 条里他说了 15 句）
- 你上一条（2 分钟前）：……
- ⚠️ 你连续发了 3 条、中间没人接。现在再接，就是在自言自语。
- 要开口，先答三问：① 这话在跟我说话吗 ② 我接上去能加什么新东西 ③ 现在再接像不像自说自话
- 三问都答不上来就别开口。这一轮不开口不算失败。
```

**关键在第一行**：把「最近 24 条里他说了 15 句」这种**客观计数**摆出来。
比任何规则都管用 —— 模型看到这个数字，会自己得出结论。

**③ 预设里加判断标准 + 分清对象**

不写「禁止回 bot」这种硬规则（那个 bot 偶尔翻车的吐槽是值得说的，禁死就变哑巴），
而是给判断依据 + 明确「真正的对话对象是人」。

### 一条更general的教训

> **想改变行为，要么改系统提示（规则），要么摆出事实（数据）。**
> 把结论写进「记忆」没有用 —— 记忆是给「这个人在意什么」用的，不是给「我该怎么做」用的。

这次的做法是**两条一起上**：预设给标准，唤醒提示给数据。
只给标准，它没有依据；只给数据，它不知道该往哪个方向判断。

## 八点七、给了工具不等于会用（2026-10-26）

这条是本次最重要的教训，同一个病在系统里出现了两次：

### 一、qq_get_prompt：3844 次工具调用里只调了 3 次

「人格卡放在 roles/ 里，唤醒提示里写一句『完整角色卡请调用 qq_get_prompt 查看』」——
实测它**几乎从不调用**。人格卡形同虚设。

修法：把核心 6 节直接并进预设的系统提示（不指望它去读）。

### 二、qq_mood：上线一天，0 次调用

心情系统给了独立工具，工具描述也写了「聊完如果有感觉就更新一下」——
**它一次都没调过。** 等于心情系统没上线。

> 结论：**「给它一个工具 + 一句建议」是最弱的约束。**
> 模型每天要处理几百轮，不会主动多做一件没人催的事。

### 修法：把动作挂到它本来就会做的事上

不新增强制流程（那会加提醒、加轮次、加噪音），而是**给收尾工具加一个可选字段**：

```
qq_mark_read({ key, throughSeq, mood: { deltas: {开心:10}, reason: "被夸了" } })
qq_set_wake_config({ key, config, mood: { deltas: {}, } })   ← 空对象 = 判断过了没变化
```

这两个工具一天被调几十次（实测 mark_read 54 次 / set_wake_config 83 次），
收尾时顺手带一个对象即可，**零额外调用**。

实测：通过 mark-read 带 `{开心:20}` → 总心情 50→52；再通过 set_wake_config 带
`{开心:15}` → 52→54。两条路径都落盘。

> 更 general 的一条：**要一个新行为真的发生，先找它已经在重复做的那件事，挂上去。**
> 再造一个新流程，等于多一个会被忽略的入口。

## 八点八、记忆检索是坏的那一环（2026-10-27）

前面花了很大力气做记忆的衰减、复活、注入，但**检索**这一环一直是对的假象。

### 原来的做法

中文没空格 → 取文本的 3 字片段，只要有 2 个片段**字面**出现在最近消息里，就算「被重新提起」。

### 实测它有多坏

拿真实的 20 条记忆，喂几句话进去：

```
「碗我洗好了，你那份也别搁着」      → ❌ 0 命中
「明天下午考试，我可能要早点睡」    → ❌ 0 命中
「那个 Amphoreus 项目怎么样了」    → ✅ 7 片段（专有名词字面重合）
「车站那边新开了家店」              → ❌ 0 命中
```

第一句最致命：记忆里明明有「白饭票梗：我发的票盖碗印…」和「谁端谁洗」，
**语义完全相关，但因为一个字都对不上，它想不起来。**

> **记忆存着却想不起来，等于没存。**

### 改成向量检索

用本地 ollama 的 `bge-m3` 算余弦相似度：

```
「碗我洗好了，你那份也别搁着」
  ✅ 0.637  「鱼拾玖说好今晚把欠的两碗白饭端来，规矩定死：真碗、图不算、谁端谁洗」
  ✅ 0.633  「扫鲸鱼嘴上认账：欠我一碗白饭，我要求端真碗不许端图」
```

**真正是那一句。** 而无关话题最高只有 0.53 —— 门槛 0.60 两边都有余量。

在真实群聊会话上跑（当时在聊「锅留就留，账别算我头上」）：

```
输入里没有「碗」「白饭」「票」任何一个字
却召回了 8 条：白饭票梗 / 白饭顶学费 / 鱼拾玖欠两碗 / 扫鲸鱼赖账 …
```

### 工程上的三个决定

**① 失败必须能退回**
ollama 没起、模型没拉、超时 —— 一律返回 `null`，调用方自动退回 3-gram。
**新功能不能变成新的故障点。**

**② 缓存必须落盘**
每条记忆的向量按文本哈希缓存（`state/emb-cache.json`），重启不重算。
一次唤醒只算 1 次「最近消息」的向量（约 20ms），其余全走缓存。

**③ 失败要冷却**
连续失败后 5 分钟内不再尝试，否则每轮都白等 10 秒超时。
这条比「重试」重要 —— **没人看着的功能，失败一次就该安静下来。**

### 两条注入路径

| 路径 | 作用 |
|---|---|
| **语义复活** | 相似度够高的记忆打上新鲜戳，下一轮排到最前（主路径） |
| **「跟现在这事有关的旧记忆」** | 相似度高但没进主列表的，单列一节补上（兜底） |

## 九、一条贯穿全部的原则

**这个系统里所有"看起来多余"的检查，都对应一次真实事故。**

| 检查 | 对应的事故 |
|---|---|
| `minProbability` 下限 | 概率被写成 0.05，95% 消息叫不醒 |
| `shouldNotifyErrorsToQQ` | 欠费时往群里刷 64 条报错 |
| `_video_tmp` 放在 workspace 内 | ffmpeg 写 %TEMP% 权限拒绝 |
| `--ffmpeg-location` 给完整路径 | 音视频分开下，静默失败 |
| 字段白名单同时改加载+保存 | `handoffText` 静默丢弃 |
| SnowLuma 只诊断不重启 | 半死实例比不启动更糟 |
| 转达留 `relayNote` | 目标会话不知道那句话为什么出现 |
| `escapeCqText` / `sanitizeQuotedText` | 引用里混进 URL 编码的 JSON 和 Markdown |

**写新功能时，先想一遍"它失败时会是什么样子"。**

如果答案是"看起来正常但实际不工作"——**那才是最危险的一类，必须加可观测性。**

## 十、如果你想继续改

**几个我想到但没做的方向：**

1. **记忆的重要性由模型自己评估** —— 现在默认 3，全靠它自己标。可以加一个"每天复盘一次，重新给本周的事打分"的机制
2. **心情的可见性** —— 现在只在注入块里给它自己看。可以做一个命令让操作者查"她现在什么心情"
3. **多群** —— 现在只进一个群。多群需要隔离记忆和注意力名单
4. **朗读** —— 语音只有输入没有输出。需要先建音色库
5. **群文件的读取** —— 有人发文档，它现在只能看到文件名

**改之前请先读这份文档的第九节。**
